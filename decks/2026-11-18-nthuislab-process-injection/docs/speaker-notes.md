## NTHU ISLab 讀書會

15 秒。打個招呼，說今天的題目方向是 Windows malware 的 process injection。

## Can You Run My Code?

45 秒。念題目和出處。
這三點只是交代「這篇在做什麼」，結論留到最後一頁。
「繞不過去的操作」先用白話帶過，講偵測條件那頁才給正式定義。

## 怎麼繞過偵測？

45 秒。先把兩邊講清楚：靜態是檔案的雜湊與特徵碼，動態是事件與 API 呼叫。
第一條就是 packer/crypter：靜態拿到的是密文，但檔案還在磁碟上，解開前後都還有東西可比；
第二條把檔案整個拿掉，payload 從網路取得後直接在記憶體載入執行，
靜態沒東西可掃，但 process 是自己開的，母子關係與呼叫序列都在動態眼下；
第三條兩邊同時對不上：靜態沒有檔案，動態雖然看得到事件，
但那些呼叫在合法 process 身上本來就會出現，混在基線裡挑不出來。
這也是三條裡最難偵測的一條，後面整場都在處理它。
為什麼放得過去：每個元件都驗簽章、都追呼叫會吃效能，
所以白名單放寬了微軟簽章的元件 —— 這個放寬就是第三條路的誘因。

## 為什麼選 process injection？

45 秒。接上一頁：第三條路裡，注入是把自己搬進對方的 address space。
第一點是遙測的歸屬問題：EDR 的事件以 PID 為單位，注入後所有紀錄都掛在目標 process 身上。
第二點：token 決定能做什麼，目標 process 權限高就一併拿到，不需要自己提權。
第三點：連線與檔案 handle 已經開好，白名單與防火牆例外也一起繼承。
最後一句是整場的轉軸：接下來三頁各示範一次呼叫序列長什麼樣。

## DLL Injection

60 秒。關鍵是：寫進去的只是一個字串，不是程式碼。
真正把 DLL 帶進記憶體的是目標 process 自己的 loader，
所以整條鏈裡最像攻擊的那一步，是由合法元件完成的。

## Process Hollowing

60 秒。本篇的主角，占 injecting 樣本的 65.5%。
第 1 步「清空」等一下會被推翻：野外主流根本不做這一步。

## Thread Execution Hijacking

60 秒。這次連「建立執行緒」都沒有。
這一步先記著，後面講偵測條件時會回來：它躲掉的是 CreateRemoteThread，但寫入那一段仍然命中，
因為偵測條件關聯的是位址，不是單一個 API 名字。
最後還要 ResumeThread，沒畫進去。

## 三種技術的呼叫鏈

90 秒。這頁是全場的地基。
橫著唸：同一件事，三種叫法。
框起來的是三個階段，框外的灰字是鋪陳與收尾。
「抽掉哪些可以、留下哪些不行」正是論文要回答的問題。
unmap 是灰的：它不在論文的配置類裡，真正的配置是下一行的 VirtualAllocEx。
這是 neurevt 省掉 unmap 也不影響判定的前提，講偵測條件時會用到。
重點是最後一行：欄會變，列不會。

## 三種技術的呼叫鏈

15 秒。停一拍，接前人的作法。

## Behavioral Signature

75 秒。先講他們做了什麼、量到多少，再解釋規則長什麼樣。
開場給名字：behavioral signature，一個已知手法一條，比對的是行為序列不是位元組。
學院一點的叫法是 specification-based detection，Petri net 就是那份規格，問到再講。
圖是 DLL Injection 那一條。
左邊三個節點是規則要的，右邊是樣本實際的呼叫，虛線是對上的那幾個。
灰字的呼叫規則不問。重點講「全部對上才算命中」這個條件。
最後一行是下一頁的入口：覆蓋範圍等於作者列舉過的做法，講完停一下。

## 不同實作的差異

90 秒。兩邊結尾的 ResumeThread 沒列，對照不需要它。
兩次映射都是惡意程式自己呼叫的，系統建立 process 時映 image 那次不算。
映射本身就把記憶體變出來，所以 trace 裡沒有 VirtualAllocEx，「配置」這一步就消失了。
這頁是前一頁的反例，也是後面「任兩個」的伏筆。
重點：不是新技術，是同一個技術的新長相。

## 偵測條件

75 秒。本篇最核心的設計決定。
分母：19.9% 是「偵測到注入的樣本」，36.1% 是其中的 Process Hollowing，PE Injection 是 29.9%。
論文 Table 6 把 NtMapViewOfSection 歸在「寫入」，不是配置。
所以 neurevt 的配置那一步在 trace 裡真的消失，映射被算成寫入，剩兩個動作照樣命中。
不會變寬鬆：兩個動作要被採信，仍然得落在同一段範圍、同一個目標 process。
不容易漏：藏一步已經不容易，攻擊者得同時把兩步都用意料之外的方式做掉。

## Elastic 的端點規則

45 秒。規則不用細讀，三件事講完就好：
一，比對的是跨 process 的呼叫序列，不是檔案內容；
二，第一行的 sequence by 就是約束：同一段位址、同一個目標 process，原文還加了 60 秒的窗口；
三，配置那段節選了三個名字，全文有五個，而且 VirtualProtect 根本不是配置而是改權限 ——
它要的是「出現一塊可執行的記憶體」這個效果，寫法上已經是 operational primitive。
最後一行是全場最有意思的對照：論文是三個操作加一個約束，這條規則是兩個操作加同一個約束。
差別在論文允許任意兩個，這條只認配置加寫入；
照名單字面看，neurevt 那種兩次 NtMapViewOfSection 的路徑，兩段都對不上。
時間點說清楚：規則 2024-07 公開，論文 2025 年發表。
第二行是我自己去清點兩個公開規則庫的結果，被問到要講得出來。
根因是 telemetry 不是語法：Splunk 的 SPL 做得到關聯，但沒有東西可以關聯 ——
它那十幾條注入偵測的來源全是 Sysmon EID 8/10/1、EID 13、PowerShell 4104 與 CrowdStrike，
而 Sysmon 根本沒有「配置記憶體」和「寫入記憶體」的事件。
三個操作裡 Sysmon 只看得見觸發執行，而且只在用 CreateRemoteThread 的時候。
注意不要講成「拿不到位址」：Sysmon EID 8 有 StartAddress，
但那是執行緒進入點，沒有配置與寫入事件可以跟它比對，所以只能當字面值用 ——
Sigma 最接近的一條就是 StartAddress 結尾等於 0B80，綁死 CobaltStrike 某個 build 的常數；
Splunk 的 StartAddress 全部出現在 stats values 裡，是秀給分析師看的欄位，不是判定條件。
Sigma 還多一層限制：它是跨後端的最小公分母格式，跨事件關聯是後來才加的，
2,427 條 Windows 規則裡只有 2 條用到。
所以 Elastic 是例外不是常態，差別在它自己掛 API hook，這反而把論文的貢獻講得更高。
另外 Sigma 的 Hollowing 規則吃 Sysmon Event 25「Image is replaced」——
照定義推論，no-unmap 變體不換掉原本的 image，應該不會觸發這個事件，
這是推論不是實測，講的時候要說清楚。

## BluePill

60 秒。投影片只列事實，解釋用講的。
左邊要補的：DBI 是執行期把分析程式碼插進指令流；
D'Elia 是這篇的第二作者，BluePill 是他 2020 年那篇的框架，不是為這篇做的。
右邊第一點要問大家：如果只有 hook，你拿不到什麼？答案是位址，而位址是偵測條件的一半。
第三點是論文的消融實驗，同一批樣本換成沒有反規避的工具就少掉快一半，
所以後面那些數字能不能看取決於這件事；侷限那頁會回來講「仍是下限」。

45 秒。投影片列事實，解釋用講的。
4 分鐘：預實驗顯示 95.2% 的樣本在 1.5 分鐘內就出現第一次注入，4 分鐘是給 DBI 開銷留的餘裕。
VM 裡放了文件、瀏覽紀錄、已安裝程式，還有模擬的網路服務，讓樣本不覺得是沙箱。
掃掉的 55 個是 debugging、monitoring、security 工具，本來就會做高權限動作，留著會汙染對照。

## 野外的注入比例

60 秒。先讓大家看那根紅柱，再報 16.5%。
16.5% 是七年合併的比例，不是逐年平均，年與年之間差到三倍，引用時要連年份一起講。
2022 的跳升和換資料來源同一年，侷限那頁會回來算帳。
前人用 behavioral signature 在 2017-2021 量到至少 9.1%，那個對照留到結論。
被問到技術分布就報：Process Hollowing 占 9,314 個注入樣本的 65.5%，
PE Injection 12.1%、Shellcode 9.6%、Passive 8.5%、Hook 4.1%、Early Bird 1.8%，
Thread Execution Hijacking 只有 1.3%，前面給它一頁是因為它最能說明「少做一個動作」。

## 技術的消長

75 秒。一頁一件事：Hollowing 吃掉其他技術，其他技術各自只紅過一兩年。
圖上這三個名字要先用一句話交代：
PE Injection 是把整個 PE 映像寫進去再自己做 relocation，reflective DLL 也歸在這類；
Passive Injection 是改登錄檔的鍵值讓別的 process 自己去載惡意 DLL，
底下涵蓋 AppInit_DLLs、IFEO、COM Hijacking 這些，攻擊者本身不碰對方記憶體；
Early Bird 是建 suspended process、寫入後掛進 APC 佇列，等執行緒進入 alertable 狀態才跑。
分母是該年偵測到注入的樣本，不是全部樣本。加總會略超過 100%，因為 3.2% 的樣本用了不只一種技術。
每條線的標籤放在自己的高點，那才是重點。
作者對每個轉折都給了歸因，挑著講：
Early Bird 2017 年 12.2%，2018 年公開討論變多之後廠商出 patch，從此歸零；
APC 幾乎絕跡，2018 年前就被 AV 認得；
Passive 在 2019–2021 衝到 40.5%，作者連到 COVID 期間攻擊暴增、攻擊者找替代手法；
PE injection 超過 shellcode，作者歸因於白皮書把進階手法寫得太清楚。
反過來說：DLL Injection from Disk 全期只有 0.4%，我們第一頁講的那個技術野外幾乎沒人用了，
但它是理解其他技術的基礎，所以還是要先講。
Atom Bombing 與 Process Doppelgänging 各只有 1 例，Extra Window Memory 是 0 例，
不過作者說他們的方法測過，這三種都抓得到。

## no-unmap 變體

90 秒。全篇最有說服力的一段。
2017 年就有 36% 的 Hollowing 樣本不呼叫 unmap，2018 年起超過原始版本。
不 unmap 的代價是 payload 落在系統給的位址，所以要自己做 relocation，
好處是 trace 裡沒有 NtUnmapViewOfSection 這個顯眼的呼叫，記憶體裡也少了破綻。
腳註那件事我去翻了他們公開的規則原始碼，不是只看論文敘述：
Hollowing 那條圖裡，NtSetContextThread 有三個輸入 place，其中一個只由 NtUnmapViewOfSection 產生，
Petri net 的轉移要等輸入全部到齊，所以少了 unmap 就永遠到不了 accepting place。
而 Thread Hijacking 那條圖允許用 NtCreateUserProcess 一次取得 process 與執行緒，不需要暫停既有執行緒。
結果就是：no-unmap 的流程完全符合 Thread Hijacking，而且必然不符合 Process Hollowing。
他們還有一個後處理「兩者同時命中就當作只有 Hollowing」，但對 no-unmap 沒用，因為它只命中一邊。
所以正確的講法是「認不出」而不是「漏掉」。

## 野外到底有多少？

75 秒。這頁是我自己把三篇擺在一起做的，論文沒有這張表。
重點只有一個：這個領域的頭條數字，主要由取樣決定，不是由野外決定。
AV 檢出門檻和注入比例幾乎單調對應 —— 四十家標記的那批有四成在注入，
三家標記的那批只有 8.3%，因為後者混進大量半死不活的樣本。
本篇的做法是依家族平衡，落在中間，這是三者裡最講得出理由的取樣。
執行時間先排除：最短的本篇反而落在中間，所以不是主因。
Korczynski 那篇要補兩句：樣本只有 934 個，而且用的是全系統污點追蹤，
不比對 API 名字，所以它的「注入」定義比另外兩篇寬，數字不能直接對齊。
但它反過來支持「16.5% 是下限」：不靠 API 名單去看，看到的比較多。
結論頁那句「16.5% 是下限」可以回來引這一頁。

## 技術組成的落差

75 秒。比上一頁更難解釋：一邊說過半是改登錄檔，一邊說三分之二是 Hollowing，年份還重疊。
Thread Hijacking 那一列的方向，正好和 no-unmap 那頁的誤標對得上：
前人多出來的 Thread Hijacking，有一部分應該就是 no-unmap 的 Hollowing。
登錄檔類 56.7% 是我把 COM 27.3%、AppInit 21.8%、IFEO 7.6% 加起來的，
前人有 5.26% 的樣本用了兩種技術，所以這個加總可能小幅重複計算。
兩邊的 Passive 定義一樣，都是 AppCert / AppInit / Shim / IFEO / COM 這五項。
這頁不下結論，把問題留到討論頁。

## 注入的對象

60 秒。右邊那個 45.3% 是我覺得全篇第二有意思的發現。
作者找資深分析師討論過，給了兩個理由：
EDR 對 process 自己的程式碼查得比較嚴，payload 放到別的 process 裡可以躲過；
寫入子 process 不必呼叫 OpenProcess，那個動作本身就很顯眼。
這也解釋了下一頁的誤判：Chrome、Skype 做的正是同一件事。

## 家族層級

75 秒。這是全篇唯一的否定結果，對做家族分類的人最有用。
結論一句話：注入技術不能拿來當家族指紋。
第一點作者自己說「似乎與 Starink et al. 相反」，前人認為家族內部是一致的。
第二點是作者的解釋：家族會隨防禦演進換技術，但換的是相近的那幾個，
例如 PE injection 和 Process Hollowing 之間互換。
第三點那四個家族：reline 是偷帳號的，幾乎每個樣本都注入；
dealply 和 allaple 樣本數都排前 20，但一個都沒有。
7,219 個樣本（12.8%）AVClass 分不出家族，這節把它們排除在外。

## 誤判

45 秒。這頁回答「拿去跑真的系統會不會亂叫」。
467 個系統程式零誤判；20 個複雜程式裡有 3 個，下一頁的侷限會講那 3 個為什麼長得像注入。
那 3 個誤判正是「任兩個操作」的代價：方法在 ResumeThread 檢查範圍，
瀏覽器 resume 的位置不在剛配置寫入的那一段，所以執行那個操作被丟掉，
但配置與寫入兩個還在，照偵測條件就算注入。
作者自己說缺的是 resumption point 的合法性驗證或 allow-list，
並且把這比作 AV/EDR 看到可疑動作後先加強監控、證據夠了才攔的做法。
最後一行是對照，數字是我去數那個檔案得到的：
82 行查詢裡真正的偵測邏輯只有兩段，其餘幾乎都在排除已知的正常軟體。
要維護那份清單就得持續追蹤哪些合法程式會踩到規則，論文這邊沒有這種東西。
開銷 1.35%、既有沙箱漏掉的比例，留到結論一起講。

## 既有方案的漏判

60 秒。這頁是 RQ3 的全部，結論頁那句「漏掉五分之一」就是這裡的平均。
兩個對照都不是弱者：VirusTotal 那邊是各家商用沙箱與掃描器的行為報告，
CAPE 是從 Cuckoo 來的開源沙箱，還掛了 Volatility 的 malfind 外掛專門找注入的記憶體。
右欄才是重點：漏掉的樣本裡有相當一部分，本方法也只看到兩個操作 ——
放寬到任兩個不是理論體操，它直接解釋了這些樣本為什麼別人抓不到。
被排除的：VirusTotal 對 2.8% 的樣本沒有行為報告，CAPE 有 59 個樣本太大跑不動。
作者的主張是整合不難，因為這些系統本來就 hook 了需要的大部分 API。

## 侷限性

90 秒。講得乾脆，不要道歉式地講。
31.6% 那批是作者另外測的 8,241 個 2021 年 Bazaar 樣本，不計入 56,340，被問到要講清楚。

## 這篇之後

60 秒。本篇 2025 年 8 月發表，到現在被引 6 次，這兩篇最相關。
第一點：XMemGuard 走 kernel，用 ETW 在 syscall 派送前攔截，
直接回應本篇「只看得到 userspace」那個限制，而且是阻擋不只是偵測。
第二點是全場最好的收尾。那篇的攻擊是把 W 和 X 拆到兩個合作的 process，
任一個單獨看都不構成「寫了又執行」，所以 Tracee、Falco 和多數 VirusTotal 引擎都沒反應，
他們拿 Mimikatz 的 shellcode 實測成功。
但把它的 Windows 流程攤開：建 section、映射進自己是 RW、遠端映射進目標是 RX、
在本地視圖 memcpy、再用 RtlCreateUserThread 在目標裡起執行緒。
照本篇的分類，遠端 NtMapViewOfSection 算寫入（Table 6），RtlCreateUserThread 算觸發執行（Table 7），
兩個操作落在同一段位址、同一個目標 process —— 就是 neurevt 那一列的形狀。
所以「任兩個操作」那個放寬不是為了多抓一點，它擋下了一個事後才出現的攻擊。
誠實話要講在前面，兩層：
一，那篇沒有對本篇做實測，上面的判斷是我自己照 Table 6/7 的分類推的；
二，它發在 ITASEC & SERICS 的 CEUR 論文集，義大利的國家級資安會議，但 CEUR 的審查比期刊輕，
所以「eBPF 和 VT 都沒抓到」那句要當作者自述來聽，他們有附 VT 的 hash，想驗可以自己去查。
但我們用的是它的機制描述，那是一份 NTAPI 的 code listing，看得懂就能自己判斷，
不必靠 venue 背書。被問到就這樣回答。
XMemGuard 那篇在 Cybersecurity，SpringerOpen 的期刊，中段但有審查有索引。

## 結論

45 秒。四句話，不要再複述前面的流程。
第一點說「認不出」不說「漏掉」：no-unmap 的樣本在前人那邊被標成 Thread Hijacking，
不是沒偵測到。64.1% 的落差另有來源，不要混為一談。
64.1% 的算法：作者把平衡方法套回前人的資料，涵蓋其中 95.6%。
差距的三個原因，被問到就講：前人沒有平衡資料集，少數家族被過度代表；
他們的系統沒有反規避（建在 VMI 沙箱上，仍可被 timing 或 stall 偵測）；
以及他們的模式太嚴，抓不到 no-unmap 這種變體。
不要講成「9.1% 變 16.5%」，那兩個數字的年份與資料來源都不同。
第二點：規則作者只需要知道規則會不會響，不會去量野外有多少人在做，這是論文的空間。
但要補一句，Elastic 是例外：它自己掛 API hook，所以看得到配置與寫入；
Sysmon 沒有那兩種事件，吃 Sysmon 的 Sigma 和 Splunk 想做也做不到。
所以「業界早就知道」這句話要收斂成「有一家看得到而且做了」。
第三點的分母要講清楚：1.35% 不是對原生執行，是對一個已經 hook 這些 API、
但不做分析的 DBI 工具。論文的論點是那些 hook 本來就得掛，偵測條件只是多一層處理。
量測條件是 worst case：Wine conformance tests 加 12 個常用 DLL 的 call-intensive workload。
第二條子項是 RQ3 的 21.2%，和開銷無關，是拿來對照「便宜卻抓得比較多」。
第四點收在誠實上：下限不只因為插樁，Detours 那個對照就是證據。
第五點是全篇唯一的否定結果，作者自己說似乎與 Starink 相反。
最後可以補論文 §6 自己的解釋，為什麼這個手法二十幾年還在用：
它利用的是正常程式也在用的合法操作，廠商不敢貿然封鎖，怕弄壞系統功能。
作者的回應是本方法只在時空吻合時才採信那些操作，所以不會誤判 —— 誤判那頁就是證據。

## 延伸問題

剩下的時間。第 1 題是我自己的方向，可以多聊。
第 2 題：那條規則 2024-07 就在 Elastic 的公開 repo 裡，早於這篇發表。
我的看法是貢獻在量測：16.5%、no-unmap 是主流，這些野外事實規則作者不會去量。
另外業界規則靠一長串路徑與 SHA256 的 allowlist 壓誤判，
論文的 3 個誤判是沒有 allowlist 的情況下量出來的，兩邊不同一回事。
第 3 題我沒有答案，只有兩個方向：
一是取樣，前人只有 VirusTotal 且沒平衡，本篇 2022 年起換 Bazaar，兩邊的母體本來就不同；
二是歸類，登錄檔那類到底算不算 process injection ——
它不碰對方記憶體，MITRE 歸在 Event Triggered Execution 而不是 T1055，
本篇自己也說要「稍微延伸記憶體配置的定義」才放得進來。
如果把登錄檔類整個拿掉重算，兩邊會不會就靠近了？這個可以現場一起算。
